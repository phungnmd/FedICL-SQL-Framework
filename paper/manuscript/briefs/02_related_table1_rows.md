# Table 1 of Related work: fact sheet for four papers

"Version read" line. A cell may carry two quotations, numbered (1) and

## Points for the editor

Against the notes:

- `notes/LITERATURE.md`, line 57 (FL4SP) says "full fine-tuning". The paper does not state it. It says "finetune T5-base" and names no adapter, so a "full" cell for FL4SP has no quotation behind it.
- `notes/LITERATURE.md`, line 59 (OpenFedLLM) gives "Llama2-7B int8, LoRA r=32". That is the instruction-tuning setup. The FedDPO runs use Wizard-Vicuna-7B-Uncensored with LoRA rank 8, alpha 16 (Sec. 4.1, footnote 1, Table 10).
- `notes/DPO_RESEARCH.md`, line 168 (OpenFedLLM) says "every FL algorithm beats local training". That holds for UltraFeedback (Sec. 4.7). On HH-RLHF, FedProx is below local training on harmlessness: HHH 72.41 against 74.14, AdvBench 19.23 against 31.35 (Table 9, p. 12; Sec. 4.8: "it fails to match the harmlessness score of local training"). The paper disagrees with itself here: the abstract says "all FL algorithms outperform local training". The same line describes FedDPO as "DPO inside FedAvg". The framework follows FedAvg, but the FedDPO table also runs FedProx, SCAFFOLD and FedAvgM.
- `notes/DPO_RESEARCH.md`, line 203 (ExCoT) has "5.6k of the 9,428 BIRD train questions". ExCoT itself gives 9.2k for BIRD train (Secs. 3.2 and 4.1). 9,428 does not come from this paper.
- `notes/DPO_RESEARCH.md`, line 56 (CodeLutra) says "base model, no SFT stage". The text says "Llama-3-8B base model" (Sec. 5.1), but the checkpoint table lists `meta-llama/Llama-3-8B-Instruct` (Table 5, p. 17). `notes/LITERATURE.md`, line 525 already records this; line 56 does not.
- `notes/LITERATURE.md`, lines 835 to 837 say federated DPO in OpenFedLLM is "All on human preferences". HH-RLHF is human preference data. For UltraFeedback the paper speaks only of "the highest score" among four LLM responses and does not say who gave the scores.

Disagreements inside the papers:

- CodeLutra says in Related work that it refines outputs "without any reliance on explicit feedback or ground-truth labels" (p. 4), and in App. A.4 "without explicit feedback" (p. 17). Its method labels samples by comparing them with the gold result (Algorithm 1, line 8), and Sec. 6 says "our framework relies on ground truth code" (p. 10). Cell 3 follows the method.
- CodeLutra's checkpoint table (Table 5, p. 17) gives StarCoder-15B (`bigcode/starcoder`), while the text and Table 3 give StarCoder-7B, and Table 1's fine-tuned rows give StarCoder2-7B. App. A.6 lists beta = 0.5 and lambda = 0.5 for the SFT baseline, which has neither term.
- CodeLutra gives two iteration rules: a fixed four iterations (Sec. 5.1) and "until the improvement ... becomes marginal" (Sec. 4).
- ExCoT gives the number of on-policy rounds as "three or more" (Sec. 3.4), as 2 in the default setup (Sec. 4.1, Table 2), and as 3 in Fig. 2. Its conclusion says "this work only applies offline-DPO" (p. 9) even though its rounds are on-policy. The abstract names "LLaMA-3 70B"; Sec. 4.1 names Llama-3.1 70B-base.
- ExCoT's gain on BIRD dev is reported from two starting points: 57.37 to 68.51 from the base model (abstract) and 58.14 to 68.51 from the SFT model (Sec. 4.2).

Where a comparison table would simplify wrongly:

- "Pairs of the model's own outputs" is not a plain yes for ExCoT. Its first DPO round uses GPT-4o pairs, and its SFT stage uses GPT-4o outputs. Only the on-policy rounds use the model's own outputs, and those outputs are chain-of-thought text, not SQL alone.
- "Labels from execution" for CodeLutra needs gold results. The executability-only variant is an ablation (Sec. 6), not the method.
- For OpenFedLLM, "fixed pairs" is our reading. The paper says only that each client holds a preference dataset and describes no step that regenerates pairs. "Not stated" is the cell that has a quotation behind it; the fixed reference model, by contrast, is stated outright.
- FL4SP has no preference stage at all. Its "labels" are exact match at evaluation time, so the cells for pairs and loss are "not applicable", not "no".
- Model size: FL4SP does not print the size of T5-base. ExCoT does not say whether it uses LoRA or full fine-tuning. A size or a "full" entry for either would have no quotation behind it.
- CodeLutra's reference model changes every iteration (pi_t). ExCoT does not state its reference model. OpenFedLLM's reference model is fixed. A single "reference" column would hold three different kinds of entry.
